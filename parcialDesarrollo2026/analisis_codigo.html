Entendiendo el Código — Desarrollo 2026 "¿Qué hace este bloque de código?"
Estos son los escenarios clásicos que los profesores usan para evaluar si entendés cómo funcionan las cosas por debajo, en vez de evaluar memoria. Elegí qué creés que hace cada bloque y lee la explicación profunda.

Caso 1: Mutación en React

const [libros, setLibros] = useState(['Harry Potter']); function agregarLibro() { libros.push('El Señor de los Anillos'); setLibros(libros); }
Al ejecutar agregarLibro(), ¿qué sucede en la pantalla?
Correcto: C. La pantalla NO se actualiza.

¿Por qué? (La explicación profunda): React necesita saber cuándo volver a dibujar (re-renderizar) la pantalla. Para no gastar recursos comparando cada elemento del array, React hace una "comparación por referencia" (pregunta: "¿Este array es el mismo objeto en memoria que antes?").

Al usar push(), modificaste el array original, pero su "caja" en memoria es la misma. Cuando le pasás ese mismo array a setLibros(libros), React dice: "Ah, me pasaste exactamente la misma caja que ya tenía. Como es la misma, asumo que nada cambió y no hago el esfuerzo de actualizar la pantalla".

La forma correcta: setLibros([...libros, 'El Señor de los Anillos']). Esto crea una caja NUEVA en memoria, y ahí React sí se da cuenta del cambio.

Caso 2: El Loop Infinito de useEffect

const [contador, setContador] = useState(0); useEffect(() => { setContador(contador + 1); });
¿Qué hace este código cuando se carga el componente?
Correcto: B. Causa un bucle infinito.

¿Por qué?: Acá tenés que entender la regla principal del ciclo de vida de React: Cada vez que el estado cambia, el componente se vuelve a dibujar (renderizar).

Al no ponerle el array de dependencias [] al final del useEffect, este efecto se ejecuta después de CADA renderizado.
La secuencia es así:
1. React dibuja la pantalla.
2. Corre el useEffect y ejecuta setContador(1).
3. Como el estado cambió, React vuelve a dibujar la pantalla.
4. Corre el useEffect de nuevo y ejecuta setContador(2).
5. Vuelve a dibujar... ¡y así hasta el infinito!

Para arreglarlo, habría que poner }, []); para que corra una sola vez.

Caso 3: Promesas y Bases de Datos (Backend)

async function obtenerUsuario(id) { const usuario = prisma.usuario.findUnique({ where: { id: id } }); if (!usuario) { return "No encontrado"; } return usuario.nombre; }
Si el usuario NO existe en la base de datos, ¿qué devuelve la función?
Correcto: C. Ignora el if. Faltó el 'await'.

¿Por qué?: Ir a buscar datos a Prisma (o usar fetch) es una operación lenta. JavaScript no se queda esperando a que la base de datos conteste. Devuelve un "pagaré" llamado Promesa.

Como la función no tiene la palabra await antes de prisma.usuario..., la variable usuario no guarda los datos del usuario, sino que guarda la Promesa (el "pagaré").

En JavaScript, una Promesa (aunque esté pendiente) siempre se evalúa como verdadera (truthy) en un if. Por lo tanto, !usuario da falso, el if se saltea, e intenta devolver usuario.nombre, que va a dar undefined porque la promesa no tiene nombre.
Regla: Siempre que hables con una BD o API externa, poné await.

Caso 4: Middleware en Express (Backend)

app.get('/api/perfil', (req, res, next) => { const tokenValido = false; if (!tokenValido) { next(new Error("Token invalido")); } res.json({ data: "Perfil secreto" }); });
¿Qué sucede al ejecutar este endpoint?
Correcto: B. Crashea por intentar responder dos veces.

¿Por qué?: En Node/Express, llamar a next(error) avisa que hubo un error y salta al errorHandler, pero no interrumpe la ejecución del resto de tu función (porque next es solo una llamada a otra función, no un `return` mágico).

Al no poner un return adentro del if, Express ejecuta next(error) (que eventualmente manda una respuesta de error al cliente), y acto seguido ejecuta res.json({ data: "Perfil secreto" }).
Como el servidor intenta responderle dos cosas distintas al cliente en el mismo ciclo HTTP, Node tira el famoso error: "Cannot set headers after they are sent to the client" y explota.

La forma correcta: return next(new Error(...));
