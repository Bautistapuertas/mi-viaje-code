Modulo 1 Fundamentos Web, Arquitecturas, Git y Scrum
1. Ciclo de Vida y Arquitectura
  • Cascada: Lineal y secuencial. No se puede volver atras facilmente. Asume que los requerimientos no cambian.
  • Agil (Scrum): Iterativo e incremental. Entrega valor constante y se adapta al cambio.
  • Escalabilidad: Vertical (mejorar hardware, CPU, RAM) vs Horizontal (agregar mas computadoras/nodos).
  • Monolitico: Todo en un solo proceso. Si falla un componente, se cae todo el sistema.
  • Microservicios: Servicios chicos e independientes. Cada uno tiene su propia logica y base de datos (aislamiento de fallos).
  • Multicapa: Cada capa (Presentacion → Negocio → Persistencia) se comunica solo con la inmediatamente inferior.
2. Requerimientos y UX/UI
  • Historias de Usuario: Requerimientos escritos desde la vista del humano. Formato: "Como [Rol], quiero [Accion], para [Beneficio]".
  • INVEST: Reglas para una buena historia: Independiente, Negociable, Valiosa, Estimable, Small (chica, clave para entrar en un sprint), Testeable.
  • MoSCoW: Tecnica para priorizar tareas cuando no hay tiempo para todo. Must (Vital, sin esto el sistema no sirve), Should (Importante, pero puede esperar), Could (Un lujo si sobra tiempo), Won't (Descartado para esta entrega).
  • Planning Poker: Busca estimar el tamaño/complejidad relativo usando cartas Fibonacci, no busca horas reloj exactas.
  • UX vs UI: UX es la experiencia completa del usuario (emociones, frustraciones, flujos). UI es lo visual en la pantalla (botones, colores).
  • Diseño: Wireframe (Baja fidelidad, puro esqueleto sin colores). Mockup (Estilo visual, tipografia, pero NO funcional). Prototipo (Alta fidelidad, ya podes hacer click e interactuar).
3. Scrum
  • Product Owner (PO): Representa al cliente y al negocio. Es el unico responsable de priorizar el Product Backlog.
  • Scrum Master: Facilita el proceso, elimina bloqueos o impedimentos, asegura que se cumplan las reglas de Scrum.
  • Daily: Sincronizacion del equipo de desarrollo (maximo 15 min). Es para coordinar el trabajo del dia, NO es un reporte de estado para el jefe.
  • Review vs Retrospective: Review = Se muestra el producto (el incremento) terminado al cliente para recibir feedback. Retrospective = El equipo mira hacia adentro y mejora su proceso de trabajo.
4. Git y JS/TS
  • Git pull: Equivale exactamente a hacer git fetch + git merge.
  • Git clone: Descarga una copia completa del repositorio, con absolutamente todo su historial de commits.
  • let / const: Reemplazan a var. Tienen scope de bloque (mueren fuera de las llaves {}). const prohibe reasignar el valor.
  • Promesas (Promise): Objeto que representa un valor futuro. Estados: pending (pendiente), fulfilled (resuelta), rejected (fallo). async/await pausa la ejecucion del codigo hasta que la promesa se resuelva, sin bloquear el navegador.
  • TypeScript: Aporta tipado estatico (detecta errores de tipo en tiempo de compilacion, antes de correr la app). any apaga los chequeos (muy mala practica), unknown es seguro porque te obliga a verificar el tipo antes de usar la variable.

Modulo 2 Frontend con React y Entorno
1. Conceptos Core
  • Virtual DOM: Es un "borrador" ligero del HTML en la memoria. En vez de borrar y repintar toda la pagina (lo cual es carisimo y lento), React compara borradores nuevos contra viejos (proceso de Diffing), encuentra la unica etiqueta que cambio, y va al DOM real a modificar SOLO esa porcion (super rapido).
  • Estado (State): Memoria interna del componente. Si el estado muta o se actualiza, el componente se re-renderiza para mostrar el cambio.
  • Props: Parametros de configuracion que un componente padre le pasa a un hijo. Son de solo lectura (el hijo no las puede modificar).
  • Inmutabilidad: En React esta terminantemente prohibido mutar el estado original (ej: libros.push(nuevo) no sirve porque React no detecta el cambio de referencia). Siempre hay que crear un array/objeto nuevo: [...libros, nuevoLibro].
2. Hooks de React
  • Regla de oro: Los hooks van siempre en el nivel superior del componente. Nunca se llaman dentro de loops, funciones anidadas o un if. React necesita saber el orden exacto en que se ejecutan en cada render.
  • useEffect: Sirve para "enganchar" efectos secundarios (cosas por fuera de dibujar la pantalla: llamados a APIs, timers, modificar el document.title).
    - Sin array: corre en CADA render (peligro de loop infinito).
    - [] (array vacio): corre una sola vez al montarse. Aca va el fetch de carga inicial.
    - [variable]: corre al montar y cada vez que variable cambia.
  • useContext: Actua como una "nube global" para evitar el Prop Drilling (pasar props de mano en mano por 10 componentes intermedios que ni las usan). Un componente muy profundo puede descargar el dato directamente desde esta "nube" sin molestar a los padres.
  • StrictMode: En entorno de desarrollo (vite), monta el componente dos veces a proposito para ayudarte a detectar efectos mal escritos. (Por eso ves el fetch doble en la consola). En produccion no pasa.
3. Routing y Formularios
  • <Link> vs <a>: La etiqueta <a> nativa hace un request HTTP nuevo y recarga toda la pagina (perdes el estado de React). El <Link> de React Router intercepta el click y cambia el componente a mostrar en pantalla sin recargar, logrando una verdadera SPA (Single Page Application).
  • Componente Controlado: Es un input (como una caja de texto) cuyo valor no vive suelto en el HTML, sino que esta atado 100% al estado de React usando value={estado} y onChange={setEstado}. React pasa a ser la "unica fuente de la verdad".
  • Zod: Libreria que permite definir "esquemas" o moldes estrictos para los datos (ej: tiene que ser un mail, minimo 5 caracteres). Sirve para validar formularios.
4. CORS y Seguridad en el Front
  • CORS (Cross-Origin Resource Sharing): Es el "patovica" de seguridad del Navegador (Chrome, Edge). Por defecto, si tu Front (puerto 5173) pide datos a otro puerto distinto, Chrome te esconde la respuesta por precaucion. El Backend debe habilitar CORS para decirle a Chrome "deja pasar a este Front, es amigo". ¡El backend NUNCA bloquea por CORS! Por eso Postman o curl nunca dan este error.
  • Preflight (OPTIONS): Cuando queres hacer un request complejo (como un PUT, o mandar un header de Authorization), el navegador frena y manda primero un request vacio tipo OPTIONS al backend para preguntar: "¿Tengo permiso de mandar esto?". Si el back dice que si, ahi recien sale el request real.
  • LocalStorage vs XSS: Guardar el JWT (token) en localStorage es conveniente, pero tiene el riesgo de sufrir ataques XSS (cualquier script malicioso inyectado en el HTML por un hacker puede acceder al localStorage y robar tu token).
  • Validacion UI (Front): Esconder un boton de "Borrar Usuario" si no sos admin es pura UX (Experiencia de Usuario), para que no clickeen en vano. No es seguridad real. La seguridad y la regla inquebrantable siempre viven en el Backend.

Modulo 3 Backend, Seguridad y Testing
1. Backend y Capas
  • Arquitectura Multicapa del Backend:
    - Routes: Actuan como el derivador. Solo ven la URL y el Metodo (POST, GET) y mandan el pedido al controller adecuado. No tienen if ni logica.
    - Controllers: Son los traductores. Toman el pedido (HTTP, params, body), se lo pasan al Service, y cuando el Service responde, eligen con que Status Code (ej: 201) y en que formato (JSON) devolverlo al front.
    - Services: Tienen la logica PURA de negocio (reglas, base de datos). No saben que existe HTTP (nunca tocan req o res ni devuelven status codes).
  • REST (REpresentational State Transfer): Es un estilo arquitectonico, una convencion. Las URLs deben usar sustantivos en plural (/api/libros), NO verbos (/api/borrarLibro esta pesimo).
  • Idempotencia: Una accion es idempotente si correrla 10 veces seguidas deja el sistema exactamente igual que si la corrieras 1 vez. PUT (reemplazo completo) y DELETE son idempotentes. POST (crear) NO es idempotente, porque si lo mandas 10 veces, creas 10 registros.
  • Status Codes: 201 (Creado), 204 (Exito pero sin contenido de respuesta, tipico de DELETE), 400 (Bad Request, error de validacion Zod), 409 (Conflicto, ej: intento de duplicar un dato o borrar un padre con hijos).
2. Base de Datos, Docker y ORM
  • Docker: Empaqueta tu app y todas sus dependencias en un contenedor aislado. Funciona igual en cualquier computadora o servidor. Diferencia clave: Una Máquina Virtual virtualiza todo el Hardware (es giganta y tarda minutos en prender), un Contenedor virtualiza solo el SO y comparte el kernel (pesa megabytes y levanta en segundos).
  • ORM (Prisma): Herramienta que mapea tus tablas de base de datos a objetos de TypeScript. Te da autocompletado y tipado. Que NO hace: El ORM no piensa por vos. No diseña tu modelo relacional, no te salva de tener que entender como funciona SQL por debajo, y no optimiza consultas complejas por arte de magia.
  • onDelete: Cascade: Regla de integridad referencial super agresiva. Si borras un registro "padre" (ej: un Autor), la base de datos se encarga de fulminar automaticamente a todos sus registros "hijos" (ej: todos sus Libros). Ideal para evitar registros huerfanos.
3. Autenticacion, JWT y Seguridad
  • 401 vs 403 (Trampa tipica):
    - 401 Unauthorized: Significa "No se quien sos". Falta el token o esta vencido.
    - 403 Forbidden: Significa "Se perfectamente quien sos, pero NO tenes el nivel de acceso (rol) necesario para entrar a esta ruta".
  • Hash vs Cifrado: El Hash (ej: bcrypt) es un proceso irreversible (entra contraseña, sale texto raro, y no existe algoritmo matematico para devolverlo a contraseña original). El Cifrado (ej: AES) es reversible si conoces la clave secreta. Las contraseñas SIEMPRE se hashean.
  • JWT (JSON Web Token): Es un formato de token que transmite informacion. Esta FIRMADO, pero NO encriptado. Cualquiera que agarre tu JWT puede decodificar el Payload leyendo la base64. Por ende, NUNCA hay que poner contraseñas o datos sensibles adentro del token. La "firma" del token existe solo para que el servidor garantice que nadie modifico el payload en el viaje.
  • SQL Injection: Ocurre cuando un hacker manda comandos SQL maliciosos a traves de tus inputs. Se previene siempre parametrizando las consultas (separando tajantemente el comando SQL del valor del usuario). Prisma te protege de esto automaticamente si usas sus metodos.
4. Testing Avanzado
  • Piramide de Testing:
    - Base (Unitarios): Prueban 1 funcion o componente completamente aislado. Son muy rapidos, baratos y haces muchisimos.
    - Medio (Integracion): Prueban varias piezas conectadas (ej: API + Base de Datos).
    - Punta (E2E): Simulan al usuario usando el navegador real (ej: Cypress). Haces pocos porque son lentisimos y caros de mantener.
  • TDD (Test-Driven Development): Es la tecnica de escribir los tests ANTES de programar. El ciclo es inquebrantable: Rojo (el test falla porque el codigo no existe) → Verde (escribis codigo super rapido y feo solo para que pase el test) → Refactor (limpias y optimizas tu codigo).
  • Mocks (ej: vi.fn()): Es crear una funcion falsa o de mentira. Te sirve para probar un componente sin necesidad de ejecutar la logica pesada real. Por ejemplo, en un test, podes crear un "mock" de la base de datos que siempre devuelva "Exito", asi probas tu Controller de forma aislada.
  • Testing Library (getBy vs queryBy):
    - getByText: Si no encuentra el texto en el DOM, entra en panico y corta/falla el test inmediatamente.
    - queryByText: Si no encuentra el texto, no lanza error, simplemente devuelve null. Es perfecto para hacer expects como expect(queryByText('Error')).toBeNull() (verificar ausencia).
