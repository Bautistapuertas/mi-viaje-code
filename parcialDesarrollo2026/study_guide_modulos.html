Modulo 1 Fundamentos Web, Arquitecturas, Git y Scrum
1. Fundamentos y Arquitecturas
  • Cliente/Servidor: El Cliente (navegador) hace peticiones (Requests) y el Servidor (backend) las procesa y devuelve respuestas (Responses).
  • API vs Web Tradicional: La web tradicional devuelve HTML completo. Una API (Application Programming Interface) devuelve datos crudos (generalmente en formato JSON) para que el Frontend los dibuje.
  • Monolitico: Toda la logica (frontend, backend, bd) corre junta en un solo proceso. Pros: facil de arrancar. Contras: si explota una cosita (ej: facturacion), se cae toda la app.
  • SOA y Microservicios: Rompen el monolito. Los Microservicios son piezas 100% independientes que hablan entre si (ej: Netflix tiene un microservicio solo para recomendaciones). Cada uno tiene su propia Base de Datos.
  • Arquitectura Multicapa (Backend): Separa responsabilidades. Presentacion (Rutas) -> Negocio (Services) -> Persistencia (DAO/BD). Una capa solo puede hablar con la de abajo.
  • Escalabilidad: Vertical (Ponerle mas RAM/CPU a la misma maquina, tiene limite). Horizontal (Agregar clones de la maquina y un balanceador de carga, limite infinito).
2. Ingenieria de Software y SDLC
  • SDLC (Software Development Life Cycle): Es el proceso que sigue todo software: Planificacion -> Analisis -> Diseño -> Implementacion -> Pruebas -> Despliegue -> Mantenimiento.
  • Modelo Cascada (Waterfall): Rigido y lineal. Tenes que terminar una fase al 100% para pasar a la otra. Problema: El cliente no ve nada hasta el final, y los requerimientos siempre cambian.
  • Modelo Iterativo e Incremental (Agil): Se divide el proyecto en entregas chiquitas (iteraciones). En cada una se pasa por todo el ciclo de vida y se entrega una pieza funcional (incremento). Permite abrazar el cambio.
3. Scrum
  • Que es: Un marco de trabajo agil. NO es una metodologia rigida, es empirico (se basa en la experiencia). Se divide el tiempo en Sprints (1 a 4 semanas maximo).
  • Product Owner (PO): Representa al cliente. Único responsable de mantener y priorizar el Product Backlog (la lista de todo lo que hay que hacer).
  • Scrum Master: "Lider servidor". Su trabajo es eliminar impedimentos que bloquean a los developers y asegurarse de que nadie rompa las reglas de Scrum.
  • Developers: Equipo multifuncional y auto-organizado (no hay "jefes" tecnicos). Estiman el esfuerzo.
  • Eventos:
    - Sprint Planning: Eligen que tareas del Product Backlog van a hacer en este Sprint (creando el Sprint Backlog).
    - Daily Scrum: 15 min diarios. Sincronizacion de devs (que hice, que hare, que me bloquea).
    - Sprint Review: Al final del sprint. Muestran el producto funcionando al cliente. Feedback.
    - Sprint Retrospective: Ultimo evento. El equipo habla de como mejorar su propio proceso de trabajo (problemas, roces, mejoras).
4. Requerimientos
  • Historias de Usuario: Requerimientos desde la perspectiva humana. "Como [rol] quiero [accion] para [beneficio]". No hablan de tablas de BD, hablan de valor de negocio.
  • INVEST: Checklist para saber si una historia esta bien escrita. Debe ser: Independiente, Negociable, Valiosa, Estimable, Small (chica para caber en un sprint), Testeable.
  • Criterios de Aceptacion: Son los "bordes" de la historia. Condiciones exactas que deben cumplirse para decir "esto esta terminado".
  • MoSCoW: Tecnica para priorizar tareas cuando hay poco tiempo. Must (Vital, sin esto el sistema no sirve), Should (Importante, pero sobrevive sin el), Could (Lujo), Won't (No se hace en este sprint).
  • Planning Poker: Forma de estimar esfuerzo en equipo usando cartas de Fibonacci (1,2,3,5,8). No estiman horas reloj exactas, estiman "esfuerzo relativo" comparado con tareas anteriores para evitar sesgos.
5. UX/UI y Diseño
  • UX (User Experience): Como se siente usar la app. El flujo, la facilidad, la prevencion de errores. Un boton rojo gigante que dice "borrar" al lado de "guardar" es una pesima UX.
  • UI (User Interface): La parte puramente visual (colores, tipografias, sombras).
  • Wireframe: Primer paso. Boceto rapido de baja fidelidad (cajas grises). Define estructura y disposicion.
  • Mockup: Segundo paso. Le suma todo el estilo visual (UI) pero sigue siendo una imagen inmovil, sin funcionabilidad.
  • Prototipo: Tercer paso. Alta fidelidad e interactivo. Podes hacer clicks y navegar como si fuera real (Figma), ideal para probar la UX con usuarios.
6. Git y JavaScript / TypeScript
  • Git (Local vs Remoto): git init crea un repo local. git clone baja un repo remoto con TODO el historial.
  • Areas de Git: Working Directory (tus archivos) -> Staging (preparados para commit via git add) -> Repository (commit guardado via git commit).
  • Comandos clave: git pull = fetch (traer cambios) + merge (fusionar). git branch crea ramas paralelas para desarrollar features sin romper la rama principal (main).
  • Asincronismo (Promesas): Una operacion (ej: ir a una BD) que demora no puede frenar el navegador. JS devuelve una Promesa (estados: pending, fulfilled, rejected). Se manejan con .then() o con async/await (mas limpio, hace que parezca codigo secuencial).
  • TypeScript: Superconjunto de JS que añade Tipado Estatico. Detecta errores al programar, no en produccion.
    - any: Le dice a TS "confia en mi, desactiva la seguridad". (Pesimo).
    - unknown: Es seguro. Te fuerza a hacer un chequeo de tipo (typeof) antes de dejarte usar la variable.

Modulo 2 Frontend con React y Entorno
1. React Core y JSX
  • Componentes: Funciones de JS que devuelven UI (JSX). Permiten reusar codigo. Siempre empiezan con mayuscula.
  • JSX: Sintaxis que mezcla HTML con JS. React lo convierte a React.createElement por debajo.
  • Virtual DOM: "Borrador" en memoria del HTML. Cuando cambia un estado, React crea un borrador nuevo, lo compara con el viejo (Diffing) y aplica solo la diferencia microscopica en el DOM real. Esto hace que React sea rapidisimo.
  • Props: Parametros que viajan de Padre a Hijo. Son inmutables (el hijo jamas puede modificarlos).
2. Estado y Hooks (useState, useEffect)
  • Reglas de los Hooks: Solo se llaman en el nivel superior del componente. NUNCA dentro de un if, for o funcion anidada, porque React confia en el orden de ejecucion para saber que hook es de que variable.
  • useState: Crea una variable que React vigila. Si cambias la variable usando su setter (ej: setContador(1)), React vuelve a ejecutar la funcion del componente (re-render) para pintar la pantalla actualizada.
  • Inmutabilidad Absoluta: Prohibido mutar el estado. Hacer array.push() es ilegal porque el array sigue siendo el mismo objeto en memoria, entonces React asume que nada cambio. Solucion: [...viejoArray, nuevoItem].
  • useEffect: Para "Efectos Secundarios" (fetches a APIs, timers, subscripciones).
    • useEffect(() => {...}) (sin array): Corre en TODOS los renders. Peligro de bucle infinito.
    • useEffect(() => {...}, []): Corre UNA sola vez (al montar). Ideal para la llamada inicial a la API.
    • useEffect(() => {...}, [id]): Corre al montar, y cada vez que la variable id cambie.
  • Cleanup Function (useEffect): Si el efecto hace un setInterval, debes devolver una funcion en el useEffect haciendo clearInterval, sino al desmontar el componente el timer seguira corriendo como un fantasma (fuga de memoria).
3. Estado Global y Contexto
  • Prop Drilling: Ocurre cuando tenes que pasar una prop del Padre al Tataranieto, pasando por el Hijo y el Nieto que ni siquiera usan esa prop. Es engorroso.
  • useContext: Crea un "almacen global" (Context Provider). Cualquier componente, sin importar que tan profundo este, puede consumir esos datos directamente sin pedirselos a su padre.
4. Enrutamiento (React Router DOM)
  • SPA (Single Page Application): Las apps de React cargan el index.html una sola vez. Cuando cambias de pantalla, JavaScript simplemente reemplaza los componentes en pantalla, sin recargar el navegador.
  • <Link> vs <a>: La etiqueta <a> nativa fuerza al navegador a hacer un pedido al servidor y recargar la pagina. <Link> intercepta ese click y le dice a React Router que cambie la URL y el componente, manteniendo la magia de la SPA.
  • Componentes clave: BrowserRouter (envuelve todo), Routes (lista de rutas), Route (define que Componente va en que path).
5. Formularios y Zod
  • Formularios Controlados: El valor del input no esta libre en el DOM, esta atado 100% a un estado de React mediante value={estado} y onChange={(e)=>setEstado(e.target.value)}. React es el dueño absoluto de lo que ves en la cajita de texto.
  • Zod: Libreria de validacion. Creas un esquema (ej: z.string().email()). Luego usas schema.safeParse(datos). Si hay error, te devuelve que falló sin crashear la app.
6. Seguridad Frontend y CORS
  • CORS (Cross-Origin Resource Sharing): Es un escudo protector que implementa tu navegador. Si tu front en localhost:5173 le pide datos al backend en localhost:3000, Chrome bloquea la respuesta. El Backend tiene que devolver unos headers especiales (CORS) diciendo "Autorizo a 5173 a leerme". Trampa de examen: ¡CORS no protege al servidor, protege al usuario! Postman no tira error de CORS porque no es un navegador.
  • Preflight (OPTIONS): Para requests complejos (PUT, DELETE, enviar un JWT), el navegador primero manda un request invisible "OPTIONS" al backend preguntando "Che, ¿me vas a aceptar esto?". Si el back dice OK, recien ahi se envia el request real.
  • LocalStorage vs SessionStorage: Local = sobrevive aunque cierres la pestaña. Session = se borra al cerrar la pestaña. Guardar el token (JWT) ahi es comodo pero riesgoso frente a ataques XSS (scripts inyectados por un hacker pueden leerlo).
  • Validacion UI (El mito): Ocultar el boton de "Borrar" si el usuario no es admin es puro UX, no es seguridad. La seguridad inquebrantable siempre debe estar en el Backend verificando si el que clickea tiene el permiso.

Modulo 3 Backend, Auth, BD y Testing
1. Node.js y Middlewares (Express)
  • Node.js: Entorno que permite correr JavaScript en el servidor (fuera del navegador). Usa un modelo Single Thread (un solo hilo) pero no se bloquea gracias a su Event Loop asíncrono.
  • Express Middlewares: Funciones que atrapan la request antes de que llegue a tu codigo. Tienen acceso a req, res y next.
    • Llamar a next() pasa el control al siguiente middleware.
    • Si olvidas llamar a next() (o responder), el request se queda colgado cargando infinitamente.
    • Llamar a next(error) ignora el resto y salta directo al Error Handler global. Ojo: no corta la ejecucion, siempre debes poner return next(error).
2. Arquitectura de 3 Capas
  • Routes: Configuran las URLs. Reciben la peticion y se la patean al Controller correspondiente. Cero logica acá.
  • Controller: Traduce el mundo Web al negocio. Agarra el req.body, se lo pasa al Service. Cuando el Service responde, el Controller formatea eso a JSON y decide que Status Code (ej: 201) devolver mediante res.status().json().
  • Service: Lógica Pura de Negocio. Hace validaciones complejas, llama a la BD. Trampa: Un Service no sabe que Express existe, por ende jamás debería recibir req o res por parametro, ni devolver status codes.
3. REST y Protocolo HTTP
  • REST (REpresentational State Transfer): Es una forma estandarizada de armar APIs. Las rutas usan Sustantivos en Plural (/api/usuarios), NO verbos. La accion ya la da el Metodo HTTP (GET para traer, POST para crear, DELETE para borrar).
  • Idempotencia: Una accion es idempotente si repetir el mismo request 10 veces tiene el mismo efecto que hacerlo 1 vez. GET, PUT (reemplaza todo) y DELETE son idempotentes. POST (crea uno nuevo) y PATCH (modifica un cachito) no lo son.
  • Status Codes Críticos:
    • 200 OK: Todo bien (ej: un GET exitoso).
    • 201 Created: Creaste un recurso con exito (un POST).
    • 204 No Content: Exito, pero no tengo datos para devolverte (tipico de DELETE).
    • 400 Bad Request: Error de sintaxis o de validacion (falló el Zod del body).
    • 404 Not Found: Ruta no existe o buscaste ID que no existe.
    • 409 Conflict: Conflicto en BD (intentas registrar un mail que ya existe o borrar a un usuario que tiene compras atadas).
    • 500 Internal Server Error: El backend explotó por un bug de codigo.
4. Docker
  • Contenedor vs Maquina Virtual: La Maquina Virtual simula Hardware entero y tiene su propio sistema operativo (muy pesado). El Contenedor virtualiza solo a nivel de software y comparte el nucleo (Kernel) de la maquina anfitriona, lo que lo hace ultra liviano, pesando megas en vez de gigas.
  • Imagen vs Contenedor: La Imagen es el "molde" inerte (el archivo dockerfile compilado). El Contenedor es la instancia de esa imagen ejecutándose (corriendo).
  • Docker Compose: Herramienta que lee un docker-compose.yml para prender multiples contenedores al mismo tiempo y conectarlos en red (ej: prender tu app de Node + la BD Postgres con 1 solo comando).
5. Bases de Datos y Prisma ORM
  • Prisma ORM: Object-Relational Mapper. Traduce tus metodos en JS (ej: prisma.user.findMany()) a comandos SQL. Provee tipado estatico de la BD en TypeScript. Protege contra Inyecciones SQL por defecto.
  • Que NO hace Prisma: No "piensa" el diseño de tablas por vos, y no puede arreglar magicamente consultas lentas si tu diseño de base de datos esta mal planteado (ej: falta de indices o queries abusivas dentro de un loop).
  • onDelete: Cascade: Regla en base de datos (y Prisma). Si tenes un Autor y sus Libros asociados, si borras al Autor, la regla en Cascada automaticamente fulmina y destruye todos sus Libros. Sirve para mantener integridad (no dejar libros huerfanos), pero es riesgoso.
6. Autenticacion, JWT y Seguridad
  • 401 Unauthorized vs 403 Forbidden:
    • 401: "No te conozco" (no estas logueado, falta el token, o vencio).
    • 403: "Se quien sos perfectamente, pero no tenes permiso/rol para estar aca".
  • Hash vs Cifrado: Para guardar contraseñas SIEMPRE se usa Hash (Bcrypt). El hash es un proceso de un solo sentido (irreversible). De contraseña a texto inentendible, pero no existe la matematica para hacer el proceso al reves. El Cifrado en cambio si es reversible si conoces la "llave" secreta.
  • JWT (JSON Web Token): Formato de token ultra comun. Se divide en 3 partes: Header, Payload (la data) y Signature (la firma).
    Regla de oro: El Payload se codifica en Base64, NO se encripta. Cualquier humano agarrando tu token puede leer que hay adentro del payload pegandolo en internet. Por ende, jamas poner passwords adentro del token. La "firma secreta" del back solo sirve para asegurarse de que nadie haya alterado o modificado los datos en el viaje (lo haria invalido).
7. Testing Avanzado
  • Piramide de Testing:
    1. Unitarios (Base): Prueban funcion por funcion totalmente aislada (usando mocks). Son rapidisimos y baratos. Tenes miles de estos.
    2. Integracion (Medio): Prueban conexiones (ej: probar si el Controller se habla bien con la BD real).
    3. E2E - End to End (Punta): Levantan un navegador real, tocan clicks, llenan formularios. Son muy lentos, inestables y caros de mantener. Solo se hacen para los flujos criticos (ej: Pagar compra).
  • TDD (Test-Driven Development): Metodologia inquebrantable de programar: Primero escribis el Test (que obviamente va a fallar = estado Rojo). Luego escribis el codigo mas feo posible solo para que el test pase y se ponga en Verde. Finalmente entras a la fase de Refactor (limpias el codigo sabiendo que el test te cuida).
  • Mocks (vi.fn): Sustituto falso. Sirve para testear unitariamente un Service aislandolo de dependencias. (Ej: en vez de que llame a la BD y tarde, le pongo un mock que miente y dice "ya fui y el usuario si existe", asi puedo probar la logica de mi Service).
  • Testing Library de React (getBy vs queryBy):
    • getByText('Cargando...'): Si no encuentra el texto, corta el test lanzando un error fatal.
    • queryByText('Error'): Si no encuentra el texto, no explota, simplemente devuelve null. Es perfecto para hacer test de aserciones negativas (ej: confirmar que el cartel de error desaparecio).
  • Coverage 100% (Mito): Tener todo el codigo cubierto por tests solo significa que la computadora "pasó por esa linea de codigo". NO garantiza la ausencia de bugs (ya que tu test podria estar escrito con validaciones/expects pesimos que aprueban cualquier cosa).
