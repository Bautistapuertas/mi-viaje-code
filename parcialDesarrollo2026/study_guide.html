Modulo 1 — Fundamentos Web, Git y Scrum (C01 a C07)
Arquitectura Cliente-Servidor y la Web
  • Cliente-Servidor: El cliente (el navegador) hace peticiones HTTP y el servidor las responde. La comunicacion ocurre a traves de una red.
  • HTTP: Protocolo que permite la comunicacion entre cliente y servidor mediante peticiones y respuestas.
  • SPA (Single Page Application): Aplicacion que carga una sola vez y actualiza el contenido dinamicamente sin recargar toda la pagina. React permite construir SPAs. Su ventaja principal es una navegacion mas rapida y sin interrupciones.
  • AJAX: Tecnica para hacer peticiones al servidor en segundo plano sin recargar la pagina, y actualizar partes especificas de la UI.
  • HTML: El lenguaje para estructurar el contenido de una pagina web.
  • CSS: El lenguaje para estilizar el HTML (colores, fuentes, Flexbox, Grid).
  • JavaScript: El unico lenguaje que el navegador entiende y ejecuta. Se incluye en HTML con la etiqueta script.
  • Servidor web: Almacena y sirve contenido web a los clientes cuando estos lo solicitan.
Git — Control de Versiones
  • git init: Crea un repositorio Git nuevo en la carpeta actual (no en GitHub, sino en tu maquina).
  • git clone [url]: Descarga una copia completa de un repositorio remoto a tu computadora, con todo su historial.
  • git add [archivo]: Mueve archivos al "staging area", preparandolos para el proximo commit. git add . agrega todos los cambios.
  • git commit -m "mensaje": Guarda una foto permanente del staging en el historial local.
  • git push: Sube los commits locales al servidor remoto (GitHub) para que otros los vean.
  • git pull: Trae los cambios del servidor remoto y los fusiona en tu rama local.
  • git branch [nombre]: Crea una rama para trabajar aislado sin romper el codigo principal.
  • git log: Muestra el historial completo de commits.
  • git status: Muestra que archivos fueron modificados pero no estan en staging (estado "modified").
JavaScript Moderno y Asincronismo
  • let / const: Reemplazan a var. const no puede reasignarse, let si. Ambas tienen scope de bloque.
  • Arrow functions: Sintaxis corta para funciones: const suma = (a, b) => a + b
  • Desestructuracion: const { nombre, edad } = persona — extrae propiedades de objetos directamente en variables.
  • Spread operator (...): Desparrama el contenido de un array u objeto. Clave en React para no mutar el estado: [...viejo, nuevoElem]
  • Promesas (Promise): Objeto que representa el resultado futuro de una operacion asincrona. Puede estar pending (esperando), fulfilled (exito) o rejected (fallo).
  • async / await: Sintaxis mas legible para manejar Promesas. await pausa la ejecucion de esa funcion hasta que la Promesa resuelva, sin bloquear el navegador.
  • fetch(): Funcion nativa que hace peticiones HTTP. Devuelve una Promesa.
TypeScript
  • Que es: Superconjunto de JavaScript que agrega tipado estatico. Se transpila a JS puro. Detecta errores en tiempo de compilacion (mientras escribis) no en ejecucion.
  • Extension de archivos: .ts para TypeScript, .tsx para TypeScript con JSX (React).
  • Tipos primitivos: string, number, boolean. Tambien existe void (funciones que no retornan).
  • any vs unknown: any desactiva toda verificacion de tipos. unknown es la version segura: acepta cualquier valor pero obliga a verificar el tipo antes de usarlo.
  • Interfaces / Types: Definen la forma que debe tener un objeto. Ej: interface Usuario { id: number; nombre: string }
Metodologia Scrum
  • Sprint: Iteracion de trabajo de 1 a 4 semanas donde se produce un incremento del producto.
  • Product Owner: Representa al cliente. Prioriza el Product Backlog (la lista total de todo lo que hay que hacer). Es la unica persona responsable de esto.
  • Scrum Master: Facilita el proceso y elimina obstaculos. No es el jefe del equipo.
  • Developers: Hacen el trabajo. Se auto-organizan.
  • Sprint Planning: Al inicio del Sprint. El equipo elige que items del Product Backlog pasan al Sprint Backlog (lo comprometido para ese sprint).
  • Daily Scrum: Reunion de 15 minutos diaria, solo para los Developers. Objetivo: sincronizarse y detectar bloqueos.
  • Sprint Review: Al final del Sprint. Se muestra el trabajo terminado al cliente.
  • Sprint Retrospective: Al final del Sprint. El equipo reflexiona sobre como mejorar su proceso (no el producto).
Modulo 2 — Frontend con React (C08 a C12)
Conceptos Core: JSX y Virtual DOM
  • Componentes: Funciones de JavaScript que retornan JSX. Son los bloques de construccion de la UI.
  • JSX: Sintaxis que mezcla HTML dentro de JavaScript. El compilador lo transforma a llamadas JS puras.
  • Props: Argumentos que se le pasan a un componente desde afuera para configurar su comportamiento o contenido. Son de solo lectura dentro del hijo.
  • Virtual DOM: React mantiene una copia ligera del DOM real en memoria. Cuando cambia el estado, compara (Diffing) y solo actualiza las partes minimas necesarias. Esto lo hace muy eficiente.
Hooks de React
  • useState: Declara una variable de estado. Cuando se actualiza con su funcion setter, React re-renderiza el componente. Una variable let comun no dispara el re-render.
  • useEffect con [] (array vacio): El codigo se ejecuta solo una vez al montar el componente. Ideal para llamadas a la API al cargar la pagina.
  • useEffect con [variable]: Se ejecuta al montar Y cada vez que esa variable cambia.
  • useEffect sin array: Se ejecuta despues de CADA render (cuidado con loops infinitos).
  • useContext: Resuelve el "Prop Drilling" (pasar props por muchos niveles de componentes). Permite que cualquier componente acceda a datos globales (ej: usuario logueado) directamente.
  • Regla clave para arrays en estado: Nunca usar .push() en el array original. Siempre crear uno nuevo: [...viejo, nuevoElem]
Routing y Formularios
  • react-router-dom: Navegacion entre "paginas" sin recargar el navegador. Usa BrowserRouter, Routes, Route y Link (en lugar de a href).
  • Formularios controlados: Los inputs estan atados al estado de React con value y onChange, dando control total sobre los valores.
  • Zod: Libreria para validar datos con esquemas estrictos. Ej: verificar que el email tenga formato correcto, o que la contrasena tenga minimo 8 caracteres.
Modulo 3 — Backend: Node, Express y Prisma (C13 a C17)
Docker
  • Que es: Plataforma para empaquetar aplicaciones en contenedores aislados. No es una maquina virtual: comparte el kernel del SO pero aísla el proceso.
  • Beneficio clave: La app se ejecuta de forma identica en cualquier entorno (el problema de "en mi maquina funciona" desaparece).
  • docker-compose: Herramienta para definir y correr multiples contenedores a la vez (ej: la app Node + la base de datos Postgres).
APIs REST — Verbos y Codigos HTTP
  • Stateless: Cada peticion debe contener toda la informacion necesaria para que el servidor la entienda, sin depender del contexto de peticiones previas.
  • GET: Leer datos. No modifica nada. Ideal para recuperar informacion sin afectar el servidor.
  • POST: Crear un recurso nuevo. Respuesta esperada: 201 Created.
  • PUT: Reemplazar un recurso existente por completo.
  • PATCH: Modificar parcialmente un recurso (solo los campos enviados).
  • DELETE: Eliminar un recurso.
  • 200 OK: Exito general.
  • 201 Created: Recurso creado exitosamente.
  • 400 Bad Request: El cliente mando datos invalidos.
  • 401 Unauthorized: No hay sesion iniciada (token faltante o invalido). Falla de Autenticacion.
  • 403 Forbidden: Hay sesion, pero el rol no tiene permiso. Falla de Autorizacion.
  • 404 Not Found: El recurso pedido no existe.
  • 500 Internal Server Error: Error inesperado en el servidor.
Express y Middlewares
  • Express.js: Framework minimalista sobre Node.js para crear APIs.
  • Middlewares: Funciones que interceptan el ciclo request-response. Tienen acceso a req (la peticion), res (la respuesta) y next (para pasar al siguiente middleware).
  • Si el middleware responde (con res.json, etc.), el ciclo termina. NO debe llamar a next().
  • Si el middleware no responde (solo valida o loguea), DEBE llamar a next() para que la cadena continue, o la peticion quedara colgada.
  • req.body: Datos enviados en el cuerpo del POST/PUT.
  • req.params: Variables en la URL como /usuarios/:id.
  • req.query: Datos despues del signo ? en la URL.
Prisma ORM y Base de Datos
  • ORM: Actua como un puente entre la programacion orientada a objetos y las bases de datos relacionales, permitiendo interactuar con la BD usando objetos de TypeScript en lugar de SQL puro.
  • schema.prisma: El archivo central donde se definen los modelos (tablas) y sus relaciones (1:N, N:M).
  • npx prisma migrate dev: El comando clave. Lee los cambios en el schema, genera el SQL, lo ejecuta en la BD y regenera el Prisma Client (el codigo TypeScript) para que tu editor reconozca los modelos.
  • Seeders (seed.ts): Script para poblar la BD con datos iniciales (ej: el usuario Admin del sistema).
Modulo 4 — Seguridad e Integracion (C18 a C19)
Autenticacion vs Autorizacion — CLAVE DE EXAMEN
  • Autenticacion (AuthN) — Error 401: Responde "quien sos?". Verifica la identidad. Si no hay token, o el token es falso/expirado, se devuelve 401 Unauthorized.
  • Autorizacion (AuthZ) — Error 403: Responde "que podes hacer?". Ocurre DESPUES de autenticar. Verifica el rol. Si sos "Cliente" e intentas borrar un registro de Admin, se devuelve 403 Forbidden.
Bcrypt — Hasheo de Contrasenas
  • NUNCA guardar contrasenas en texto plano. Se guarda un hash generado por bcrypt.
  • Irreversible: No existe funcion "desencriptar". El servidor nunca sabe tu clave original.
  • Como verifica el login: Al ingresar la clave, bcrypt aplica el mismo algoritmo y compara si los hashes coinciden. Funcion: bcrypt.compare(claveIngresada, hashGuardado)
  • Salt: Texto aleatorio agregado antes de hashear. Hace que dos usuarios con la misma clave tengan hashes distintos.
  • Costo: Bcrypt es intencionalmente lento (~60ms) para que un ataque de fuerza bruta sea inviable.
JWT (JSON Web Tokens)
  • Que es: Mecanismo para mantener la sesion de forma stateless. El servidor le da un token al cliente al loguearse, y el cliente lo adjunta en cada peticion futura.
  • Estructura: Tres partes separadas por punto: Header (algoritmo), Payload (datos del usuario), Signature (firma digital).
  • FIRMADO, no encriptado: Cualquiera puede decodificar el Payload (esta en Base64). Nunca guardes datos sensibles ahi. La seguridad viene de la Firma: si alguien modifica el payload, la firma deja de coincidir y el servidor rechaza el token.
  • Ventaja sobre sesiones tradicionales: Es stateless. El servidor no necesita guardar sesiones en la BD.
OAuth y MFA
  • OAuth: Protocolo para delegar autorizacion de forma segura (ej: "Iniciar sesion con Google"). Permite que una app acceda a recursos de otra en nombre del usuario sin ver su contrasena.
  • MFA (Autenticacion Multi-Factor): Agrega capas de seguridad ademas de la contrasena. Factores: algo que sabes (contrasena), algo que tenes (token fisico), algo que sos (biometria). El email solo NO es un factor MFA.
CORS e Integracion Frontend-Backend
  • CORS (Cross-Origin Resource Sharing): Los navegadores bloquean peticiones entre origenes distintos por defecto. El backend debe instalar el middleware cors para permitir que el frontend (ej: localhost:5173) le haga peticiones.
Modulo 5 — Testing (C20 a C21)
Las diapositivas C20 y C21 todavia no estan en la carpeta. Este modulo cubre el contenido estandar de la materia para esas clases. Cuando las tengas, se puede ampliar.
Tipos de Tests
  • Test Unitario: Prueba la unidad mas pequena de codigo de forma aislada (una funcion, un componente). No dependen de la red ni de la BD.
  • Test de Integracion: Prueba como multiples unidades interactuan entre si (ej: un endpoint de Express + la base de datos).
  • Test End-to-End (E2E): Simula el flujo completo del usuario (hacer login, navegar, agregar un producto, etc.).
Vitest / Jest
  • describe(): Agrupa un conjunto de tests relacionados bajo un nombre descriptivo.
  • it() / test(): Define un caso de prueba individual. Son sinonimos.
  • expect(): Hace la asercion (la verificacion del resultado). Ej: expect(resultado).toBe(200)
  • Mocks: Reemplazos falsos de modulos o funciones para aislar la unidad bajo prueba (ej: simular que Prisma devuelve un usuario sin tocar la BD real).
React Testing Library (RTL)
  • Filosofia: Probar lo que el usuario ve y puede hacer, no como esta implementado internamente.
  • render(): Renderiza un componente en un entorno de prueba.
  • screen.getByText(): Busca un elemento en la pantalla por su texto visible.
  • userEvent / fireEvent: Simula interacciones del usuario (clics, escritura en inputs).
